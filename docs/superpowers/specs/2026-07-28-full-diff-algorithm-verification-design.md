# Full Diff 알고리즘 검증 설계

## 목적

Full Diff 화면에서 Myers, Minimal, Patience, Histogram을 선택했을 때 실제
Git diff가 다시 계산되고 화면도 해당 결과로 바뀌는지 한 번만 정밀하게
검증한다. 영구 테스트나 샘플 저장소는 남기지 않고, 재현 자료와 판정은
독립 실행 가능한 HTML 보고서에 담는다.

이번 작업은 검증과 보고가 범위다. 결함을 찾더라도 제품 코드는 고치지 않고
재현 절차, 실제 결과, 영향 범위를 보고서에 기록한다.

## 현재 검증 공백

현재 코드는 알고리즘별 Git 옵션을 `git diff`에 전달하고, 컨트롤러가 새
patch를 받은 뒤 화면 상태를 바꾸도록 구성되어 있다. 기존 테스트는 두
구간을 따로 확인한다.

- Git 계층 테스트는 `--diff-algorithm=<name>` 인수를 확인한다.
- 화면 테스트는 가짜 저장소가 알고리즘별 문자열을 반환하게 해서 화면
  갱신을 확인한다.

따라서 실제 Git 출력이 파싱되고 Full Diff 화면에 그려질 때까지 이어지는
전체 경로는 아직 하나의 검증으로 묶여 있지 않다.

## 검증 대상

다음 네 가지 구체 알고리즘을 모두 검증한다.

| 선택값 | Git 인수 |
| --- | --- |
| Myers | `--diff-algorithm=myers` |
| Minimal | `--diff-algorithm=minimal` |
| Patience | `--diff-algorithm=patience` |
| Histogram | `--diff-algorithm=histogram` |

저장소의 `diff.algorithm` 설정은 별도 알고리즘이 아니므로, 설정값이 네
가지 중 하나로 올바르게 해석되는지만 보조 항목으로 확인한다.

## 임시 샘플 저장소

`/tmp` 아래에 검증 전용 Git 저장소를 만든다. 기준 커밋과 변경 커밋에는
반복되는 함수 블록, 위치를 바꾼 블록, 고유한 기준 행을 섞은 코드 파일을
둔다. 이 구조는 알고리즘이 일치 행을 고르는 방식에 따라 서로 다른 hunk를
만들기 쉽다.

샘플은 다음 순서로 고른다.

1. 작은 코드 블록 순열 후보를 만든다.
2. 네 알고리즘으로 실제 `git diff`를 실행한다.
3. Git 헤더를 제외한 diff 본문의 SHA-256을 계산한다.
4. 네 알고리즘의 본문이 모두 구분되는 후보를 선택한다.
5. 선택한 기준 파일과 변경 파일을 각각 커밋한다.

후보를 충분히 탐색해도 네 결과가 모두 달라지지 않으면 그 사실을 숨기지
않고 실패 항목으로 기록한다. 보고서에는 선택한 두 커밋의 해시와 파일
내용을 모두 넣어 재현할 수 있게 한다.

## 검증 흐름

한 알고리즘마다 같은 커밋과 파일을 사용해 다음 경로를 확인한다.

  <div class="box">GitRepository.loadDiff</div>
  <div class="box">실제 git diff</div>
  <div class="box">DiffDocument 파싱</div>
  <div class="box">FullDiffSessionController 상태 교체</div>
  <div class="box">Full Diff 화면 렌더링</div>
</div>

검증은 세 겹으로 구성한다.

### 1. Git 원본

직접 실행한 `git diff --diff-algorithm=<name>` 결과를 기준값으로 저장한다.
알고리즘별 본문 해시, hunk 수, 추가·삭제·문맥 행 수를 계산한다.

### 2. 앱 데이터 경로

제품 코드의 `GitRepository.loadDiff`를 실제 임시 저장소에 연결한다. 반환한
`DiffLine`과 Git 원본을 같은 방식으로 정규화해 행 종류, 행 번호, 본문이
일치하는지 확인한다.

### 3. 화면 경로

실제 저장소를 사용하는 `FullDiffSessionController`로 Full Diff 작업
영역을 띄운다. 알고리즘 선택 메뉴를 눌러 네 값을 차례로 선택하고 다음을
확인한다.

- 선택한 알고리즘 이름이 툴바에 표시된다.
- 로딩이 끝난 뒤 hunk와 diff 행이 해당 알고리즘 결과로 교체된다.
- 화면에 보이는 diff 본문이 같은 알고리즘의 `DiffDocument`와 일치한다.
- 직전 알고리즘의 전용 행이 남지 않는다.
- Myers → Minimal → Patience → Histogram → Myers 순서로 바꿨을 때 처음과
  마지막 Myers 결과가 같다.

각 상태는 같은 크기의 화면으로 캡처한다.

## 판정 기준

다음 조건을 모두 만족하면 통과다.

1. 네 Git 명령이 모두 성공한다.
2. 네 diff 본문 해시가 서로 다르다.
3. `GitRepository`가 반환한 행이 각 Git 원본과 일치한다.
4. 컨트롤러의 요청값과 적용값이 선택한 알고리즘으로 바뀐다.
5. 화면의 알고리즘 이름, hunk, diff 본문이 각 적용 결과와 일치한다.
6. 알고리즘을 다시 선택해도 이전 결과가 화면에 남지 않는다.
7. 마지막에 다시 선택한 Myers 결과가 처음 결과와 같다.

하나라도 충족하지 못하면 전체 결과를 실패로 표시하고, 실패한 계층과 실제
값을 보고서에 남긴다.

## HTML 보고서

최종 보고서는 외부 자원 없이 열리는 HTML 한 파일로 만든다. 다음 내용을
포함한다.

- 실행 환경과 Git·Flutter 버전
- 샘플 저장소의 커밋 그래프와 두 버전의 전체 코드
- 알고리즘별 Git 명령과 원본 diff
- 본문 해시, hunk 수, 행 수 비교표
- 앱 파싱 결과와 Git 원본의 일치 여부
- 알고리즘별 Full Diff 화면 캡처
- 화면을 순서대로 전환한 결과와 캐시 오염 여부
- 계층별 통과·실패 판정과 최종 결론
- 검증 내용을 되짚는 문제 다섯 개

화면 캡처는 data URI로 넣어 HTML 파일 하나만 이동해도 볼 수 있게 한다.

## 정리

검증이 끝나면 임시 Git 저장소, 임시 Flutter 테스트, 중간 JSON과 화면
이미지를 제거한다. 제품 코드는 바꾸지 않는다. 저장소에는 이 설계 문서,
구현 계획, 최종 HTML 보고서만 남는다.
