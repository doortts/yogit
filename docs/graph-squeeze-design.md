# 그래프 컬럼을 좁힐 때 레인이 밀리기 시작하는 지점

2026-08-09 · 목업: `docs/graph-squeeze-mockup.html` · TDD

## 증상

컬럼 구분선을 왼쪽으로 끌면, 화면에서 가장 오른쪽에 있는 아바타가 **아직 선 근처에도
가지 않았는데** 레인이 좁아지기 시작한다. 눈에는 "빈 자리가 이만큼 남았는데 왜 벌써 밀리지"로
읽힌다.

## 녹화 실측 (2026-08-09, `column-resizing.mov`, 레티나 2배 → pt 환산)

정지 상태:

| 항목 | 값 |
|---|---|
| 레인 0·1·2 중심 x (device px) | 511.5 / 571.5 / 631.5 |
| 레인 간격 | 60px = 30pt (기본값 그대로) |
| 화면에 그려진 가장 깊은 레인 | **3** (아래쪽 노란 노드 x=691.5) |
| 컬럼 왼쪽 경계 / 구분선 | 455.5 / 902 → 폭 **223pt** |
| 마지막 노드 오른쪽 끝 ~ 구분선 | **95pt** 비어 있음 |

드래그 중:

| t | 구분선 x | 폭(pt) | 잰 간격(pt) | `deepest=6`으로 계산한 값 |
|---|---|---|---|---|
| 3.4 | 900 | 222 | 30 | 30 |
| 3.6 | 881 | 213 | 28.5 | 28.6 |
| 4.2 | 829 | 187 | 24.25 | 24.3 |
| 5.4 | 672 | 108 | 12 | 12 (바닥) |

간격이 처음 줄어드는 폭이 **221pt**이고, 이 값은 `contentWidth(6) = 28 + 6×30 + 13`과
정확히 같다. 이후 모든 프레임의 간격도 `deepest=6`으로 계산한 값과 소수점까지 맞는다.

## 원인

압축 계산에 들어가는 깊이가 **6**인데 화면에 그려진 깊이는 **3**이다. 보이는 깊이대로면
압축은 폭 131pt(`contentWidth(3)`)에서 시작해야 하는데 221pt에서 시작하니 **90pt 일찍**
밀린다. 그 깊이를 만드는 곳은 두 군데다.

**하나. 화면 밖 한 행을 센다.** `_updateRatchet`(lib/timeline_data.dart)은

```
last = ceil((pixels + viewportDimension) / rowHeight)
```

로 마지막 행을 잡는다. 뷰포트 바닥에 걸친 행의 인덱스는 `ceil(...) - 1`이므로 이 식은 화면
아래로 완전히 벗어난 행을 하나 더 센다. 그 한 행이 머지 커밋이면 레인이 한꺼번에 여러 개
열린다.

**둘. 래칫은 넓어지기만 한다.** 깊은 구간을 한 번 지나가면 얕은 곳으로 돌아와도 그 깊이가
남는다. 컬럼 폭이 스크롤마다 오르내리지 않게 하려고 그렇게 뒀는데, 같은 값이 **압축 시작
판정**에도 쓰이고 있다.

`nextLanes`는 그 행 자신의 셀 아래쪽 절반에 그려지므로 세는 것이 맞다 — 화면 밖이 아니다.
직전 진단에서 "화면 밖 2행"이라고 한 것은 1행이 맞다.

`hashRailClearance`(3pt)는 90pt 중 3pt짜리 이야기라 원인이 아니다.

## 고치는 방법

깊이를 **두 개**로 나눈다. 한 상수가 두 가지 일을 하고 있는 것이 문제였다.

| 쓰이는 곳 | 쓸 깊이 | 이유 |
|---|---|---|
| 자동 맞춤 폭 `contentWidth` (최초 폭, 더블클릭 맞춤) | 래칫 깊이 (지금대로 넓어지기만) | 스크롤마다 컬럼 경계가 흔들리면 읽기 어렵다 |
| 압축 시작·압축 계산 `spacingFor` | **지금 화면에 보이는 깊이** | 사용자가 보는 것과 밀리는 시점이 같아야 한다 |

그리고 `last`의 off-by-one을 고친다.

```
last = ceil((pixels + viewportDimension) / rowHeight) - 1
visible = 그 범위에서 잰 깊이        // 매번 새로 잰다
ratchet = max(ratchet, visible)      // 넓어지기만 한다
```

스크롤할 때 레인이 흔들리지 않나 — 자동 맞춤 폭은 `contentWidth(ratchet) ≥
contentWidth(visible)`이라 압축 단계에 들어가지 않는다. 사용자가 직접 좁혀 둔 폭에서만
`visible`이 실제로 쓰이고, 그때는 깊은 구간으로 내려가면 더 좁아지는 것이 맞는 동작이다.

## 세 단계 (화면에 레인 3개, 간격 30 기준)

| 단계 | 폭 | 보이는 일 |
|---|---|---|
| 1 여유 | ≥ 131 | 레인 제자리, 남는 자리만 줄어듦 |
| 2 압축 | 131 → 56 | 아바타가 선을 밀며 함께 왼쪽으로, 간격 30 → 12 |
| 3 접힘 | ≤ 56 | 모든 레인이 첫 레인 자리로, 곡선 없음 |

지금은 1단계가 화면 밖 레인까지 친 221pt에서 끝난다. 바닥(`minLaneSpacing` 12)과
3단계 접힘(`compactWidth` 56)은 그대로다.

## 계약 테스트

1. 뷰포트 바닥에 걸친 행 **다음 행**이 깊어도 자동 맞춤 폭은 그대로다 (off-by-one).
2. 깊은 구간을 봤다가 얕은 곳으로 돌아오면 컬럼 폭은 유지되지만(래칫), 그 폭에서 레인
   간격은 **기본 간격**이다 — 보이지 않는 깊이로 압축하지 않는다.
3. 사용자가 컬럼을 좁힐 때, **보이는 가장 깊은 노드**의 오른쪽 끝이 컬럼 경계에 닿기
   전까지 레인 x좌표가 움직이지 않는다.
4. 거기서 더 좁히면 레인이 왼쪽으로 밀린다.
5. 얕은 곳으로 돌아온 뒤 좁히면, 압축 시작점이 **그 화면의 깊이** 기준이다 (래칫 깊이가
   아니다).
6. 바닥과 접힘은 그대로: `spacingFor(...) >= minLaneSpacing`, `compactWidth` 이하에서 접힘.
7. 기존 계약 유지: 첫 화면은 보이는 레인에만 맞고, 깊은 구간으로 내려가면 넓어지고,
   사용자가 끈 폭은 어떤 스크롤에도 유지된다.

## 이어서 나온 두 가지 (2026-08-09, 앱에서 확인)

위 수정을 넣고 앱을 켜 보니 두 가지가 더 나왔다. 원인이 각각 다르다.

### 구분선이 마우스보다 늦게 따라온다

드래그가 델타를 **리사이저 위젯이 build될 때의 폭**에 더하고 있었다.

```dart
onHorizontalDragUpdate: (details) => _resizeBy(column, width, details.delta.dx)
```

마우스가 빠르면 한 프레임 사이에 move 이벤트가 여러 번 온다. 전부 같은 낡은 `width`를
기준으로 계산하니 마지막 하나만 남고 앞의 것은 버려진다 — 폭이 커서 이동량의 일부만
따라가고 뒤처진다. 테스트로 재현하면 pump 없이 6pt씩 네 번 움직였을 때 24pt가 아니라
6pt만 움직였다.

`_liveWidth(column)`으로 **이벤트 시점의 폭**을 읽는다. graph만이 아니라 모든 컬럼에
있던 문제다. 키보드 리사이즈 경로도 같이 고친다.

참고: GRAPH의 왼쪽 선은 BRANCH/TAG의 리사이저다 — 리사이저는 각 컬럼의 오른쪽 가장자리에
붙는다. graph를 좁히려면 HASH와의 경계를 끈다.

### 한 레인짜리 히스토리가 빈 컬럼을 끌고 다닌다

`_graphColumnWidth`의 자동 맞춤이 `.clamp(96.0, max)`였다. 한 레인이면
`contentWidth(0)` = 28 + 13 = 41pt면 되는데 96까지 올라가 55pt가 비어 있었다.

41까지 내리면 `compactWidth`(56) 아래라 3단계 접힘에 들어가고, 그러면 레일이 브랜치 색
대신 커미터 색으로 그려진다. 그래서 하한을 `minAutoFitWidth = compactWidth + 1` = 57로
둔다. 접힘은 사용자가 끌어서 들어가는 상태로 남는다.

계약: 8. 여러 move가 한 프레임 안에 와도 구분선은 그 합만큼 따라간다.
9. 한 레인짜리 히스토리는 `minAutoFitWidth`로 열린다.
